# Shared execution rules for Auralis integration goals

Updated: 10 October 2026. These rules accompany each module objective. A request
to prepare these prompts does not start their implementation. On a later explicit
execution request, create or continue the appropriate Goal using the available
tool contract; do not invent a token budget, extra chats or delegated agents.

## Read and freeze the endpoint

Read the applicable AGENTS instructions, the actual repository state,
docs/integration/README.md, docs/integration/architecture.md,
docs/integration/boundary-contract.md and the selected goal objective before
changing code. Read each component's authoritative plans,
current status and existing acceptance records. The integration design is in
Auralis; PUZA component documentation remains under CONTRACT/Docs. Resolve old
T:/PUZA references against the current sibling repositories after checking their
identity; do not restore historical workspace layouts.

Current checkout roots are under E:/Anything/Projects/Commercial: auralis,
auralis-translate, CONTRACT, TTS and CASTER. These are development locations, not
installed runtime paths. If a future session uses different roots, locate and
verify the repositories rather than hardcoding these paths into product code.

Inspect branches, remotes, dirty diffs and packaged/runtime identities. Preserve
unrelated changes and original media, subtitle files, voice references and accepted
results. Work against isolated test data and owned copies of databases. Do not
reset or stage unrelated changes. Do not update a submodule to uncommitted sibling
code and call that a reproducible release.

Freeze a finite task list, required gates, selected formats, engines and profiles,
resource budgets, experiment identities and external review prerequisites before
execution. Use stable INT task IDs for integration work. Translate tasks remain
in its canonical IMPLEMENTATION_BACKLOG; link them instead of duplicating status.
Update an agreed contract before changing its behavior and retain old baselines.

## Work and resource control

Execute bounded implementation slices and verify their observable acceptance.
Do not stop at scaffolding, mock demonstrations or another rewritten roadmap.
Use Taskfile commands where available and add a suitable task before a new probe.
Run model-free checks first. Model loading, inference, renders and model doctors
must be strictly sequential, with one machine-wide admission covering all engines
and external servers. Prove absence of a competing model server before launch;
if state cannot be established, continue independent work without starting one.

No Marker product integration, WPF changes, new ASR stage, training run, cloud
rental or new language support is implied. CONTRACT is a lightweight dependency.
TTS does not require running Caster; Caster does not require running TTS for its
mandatory catalog and casting acceptance. Selected input data can be explicit,
reviewed fixtures. Mocks cover engineering contracts only.

Use one core implementation for each operation across CLI and worker modes.
Keep modules small, typed and responsible for one concern. Keep Rust domain/core
independent of IO and transport; use the existing application, ports and adapters.
Do not build a general plugin framework or rewrite working inference algorithms
without a measured defect. Compatibility facades preserve existing public APIs.

## Evidence and completion

Add meaningful regression tests for new failure boundaries, identity checks,
checkpoint ordering and recoverable publication. Retain reproductions and failed
attempts. Real experiments predeclare inputs, hashes, profiles, run counts, time
and resource limits, expected invariants and stop criteria. Freeze retry limits;
do not regenerate until a preferred answer happens to appear.

Record commands and exits, code identity including dirty hashes, runtime/model
identity, hardware, source/result hashes, stage timings, approximate resource
samples and failures. Language quality needs source-aware review; speech quality
needs actual listening with declared coverage. Never invent a reviewer or promote
an unverified voice. Missing assets, reviewers or clean-machine access leave
their gates open while independent tasks proceed. Goal blocking follows the
actual Goal tool's threshold; a single missing input is not automatic goal completion.

Use the machine's primary global Git author and committer identity, inspected
against local and environment overrides. Follow the session commit and PR rules.
Create scoped commits only after reviewing their contents. Publish only to the
destination authorized for that execution; this prompt does not order a merge,
production deployment or changes to unrelated originals.

Audit one committed candidate and its exact package/schema/profile pins after
final fixes. Run affected checks again when candidate identity changes. Mark the
selected goal complete only when every required gate has evidence. Report exact
task commands, observed outcomes, candidate identity and remaining exclusions.
An integration milestone does not imply a broader language, voice or platform
release, and missing mandatory real evidence cannot be deferred to claim success.
